Storage posture (PCP-24264):
{{- /* PCP-24264 review: REDACT any userinfo before printing. The shipped lite default is a bare
       file path, but DATABASE_URL is operator-settable through BOTH lite.config and the shared
       global map, and this line goes to `helm install` output, to `helm get notes`, and to every
       CI log that captures either. A URL carrying inline credentials would be echoed in full.
       Anchored on `://`, and the class is `[^/]*` -- NOT `[^@/]*`. Excluding `@` made the match
       stop at the FIRST one, so a password containing an unencoded `@` (`//u:p@ss@host/db`) had
       only `//u:p@` replaced and leaked the `ss` tail in clear. `[^/]*` is greedy to the LAST
       `@` before the first `/`, which is exactly RFC 3986's userinfo boundary, so the whole
       credential goes. Still cannot cross a path separator, so a path or query containing `@`
       is left alone.

       TWO passes, because a credential reaches this line by two different routes and the first
       pass only closes one of them. Userinfo (`//user:pass@host`) is the obvious one; the second
       is a QUERY PARAMETER — `?password=…`, which is how libpq, ODBC and several drivers accept
       a secret, and which has no `@` for the first pattern to anchor on. Case-insensitive, and
       bounded by `[^&]*` so it redacts one parameter rather than the rest of the string. The
       allow-listed names are only the credential-bearing ones, so this ticket's own
       `?uri=true&vfs=unix-dotfile` is left intact — a redactor that ate the VFS marker would
       hide the very fact this advisory exists to show.

       `sslpassword` and `sslkey` are listed SEPARATELY and FIRST, which looks redundant next to
       `password` but is not: the alternation is anchored on `[?&]`, so `[?&]password=` cannot
       match `?sslpassword=` — the parameter name has to match from its first character. libpq
       accepts `sslpassword`, so without its own entry that secret printed in clear (review round
       10, @adhanshe-tibco). They are ordered ahead of the shorter names because Go's regexp is
       leftmost-FIRST, not leftmost-longest, so a shorter alternative that could match at the same
       offset would win; the `[?&]` anchor already makes that unreachable here, and the ordering
       keeps it unreachable if the anchor is ever loosened.

       NOT fixed, deliberately: a `/` inside the userinfo (`//u:p/w@h/db`) still defeats the first
       pass. Per RFC 3986 the authority ends at the FIRST `/`, so in that string the userinfo is
       absent and `u:p` is the host:port — the bytes a wider pattern would "redact" are a HOST, not
       a credential. Widening `[^/]*` to `[^?#]*` would also redact `@` appearing in an ordinary
       path. Redacting a hostname to protect an out-of-spec URL is a worse trade than leaving it. */}}
  Database URL : {{ regexReplaceAll "(?i)([?&](?:sslpassword|sslkey|password|passwd|pwd|secret|token|api[-_]?key)=)[^&]*" (regexReplaceAll "://[^/]*@" (dig "DATABASE_URL" "(unset — the image default applies)" $liteCfg | toString) "://<redacted>@") "${1}<redacted>" }}
  Data PVC     : {{ .Release.Name }}-mcp-gateway-data ({{ .Values.lite.storage.size }})
  StorageClass : {{ if $scNone }}"" (no dynamic provisioning — this PVC binds a pre-provisioned PV){{ else if $sc }}{{ $sc }}{{ else }}(unset — the cluster DEFAULT class provisions this PVC){{ end }}
  Declared     : {{ if $kind }}{{ $kind }}{{ else }}(undeclared — global.tpMcpGateway.storage.classKind){{ end }}

  A lite gateway keeps ALL of its state in ONE SQLite file on that PVC. Read what the class
  really is off the cluster — never infer it from the name (TIBCO's own share-backed class is
  named `azure-files-sc`, and block-backed names mention "file" too):
{{- if $scNone }}
    kubectl describe pv $(kubectl get pvc {{ .Release.Name }}-mcp-gateway-data -o jsonpath='{.spec.volumeName}')
  (there is no StorageClass object to read in this configuration — the volume source and the
  mountOptions live on the pre-provisioned PV, which is what that command prints. `describe` and
  not a `-o jsonpath` on `.spec.csi.driver`: a pre-provisioned PV may use an IN-TREE source —
  `nfs`, `azureFile`, `cephfs`, `glusterfs` — instead of `csi`, and against those a csi-driver
  jsonpath prints an empty string. That reads as "inconclusive" for precisely the share-backed
  volumes this advisory exists to catch, which is the one direction it must not fail in.
  `describe` names whichever source the PV actually has.)
{{- else }}
    kubectl get sc {{ if $sc }}{{ $sc }}{{ else }}<class>{{ end }} -o jsonpath='{.provisioner}{"\n"}{.mountOptions}'
{{- end }}
  A provisioner of file.csi.azure.com — or any other SMB/CIFS/NFS provisioner — means the
  volume is share-backed and CANNOT host a WAL SQLite database: the share refuses SQLite's
  SHARED→EXCLUSIVE byte-range lock upgrade (fcntl F_SETLK → EACCES) and the pod CrashLoops
  on "database is locked". The gateway detects that at startup and converts the volume to the
  unix-dotfile VFS + rollback journal by itself (DB_SQLITE_NETWORK_FS=auto; set it to "off" to
  roll back with no image change), logging ONE warning naming the fstype, the probe verdicts
  and the VFS it chose. Nothing to do by hand.

  Two PLATFORM answers are strictly better where you control storage, because neither gives up
  the read concurrency the dotfile VFS costs:
    • a block-backed class      --set lite.storage.className=<block-class>
    • `nobrl` in that class's mountOptions (measured: the default VFS AND WAL both work again)
  Both apply to NEWLY provisioned volumes only — a PV records spec.mountOptions when it is
  created, so neither is retroactive to a PVC that already exists.
